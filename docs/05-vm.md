# 05 虚拟机与 MicroVM

## 1. 为什么硬件虚拟化是更强的边界

前面所有方案（软沙箱、容器、gVisor）最终都依赖**同一个宿主内核**的正确性。虚拟机则引入硬件强制的边界：

```
┌─────────────────────────────────────────────┐
│ Guest 应用（不可信代码）                      │
│ Guest Linux 内核（独立内核，崩了也只崩 VM）   │
├─────────────────────────────────────────────┤
│ 硬件虚拟化边界：VT-x / AMD-V + EPT/NPT       │
│  - Guest 代码跑在非特权 ring，敏感指令 trap   │
│  - 内存由二级页表(EPT)隔离，Guest 只见自己的  │
├─────────────────────────────────────────────┤
│ VMM（Firecracker / QEMU / Cloud Hypervisor） │
│  用户态进程，暴露极小的攻击面                 │
├─────────────────────────────────────────────┤
│ 宿主内核 + KVM                               │
└─────────────────────────────────────────────┘
```

逃逸条件从"宿主内核漏洞"变成"**VMM 漏洞或 hypervisor 漏洞**"。而现代 microVM 的 VMM 刻意做得极小（Firecracker ~5 万行 Rust，QEMU 数百万行 C），攻击面差距是数量级的。

## 2. MicroVM：为云原生削薄的 VM

传统 QEMU VM 慢在"模拟了一台完整 PC"：BIOS/UEFI、PCI 总线、USB、显卡、软驱……microVM 的思路是**砍掉一切不需要的设备模型**：

- 无 BIOS，直接加载内核（linux boot protocol）；
- 只有 virtio-net / virtio-block / virtio-vsock 等几个设备；
- 无 PCI 枚举（或极简）、无 USB/显示/音频；
- VMM 本身再用 seccomp + jailer 关进沙箱（纵深防御：VMM 也是不可信面）。

### 2.1 Firecracker（AWS 开源，Rust）

- 支撑 **AWS Lambda 与 Fargate** 的多租户隔离；
- 启动 **~125ms** 到 userspace，内存底噪 **<5MB/VM**，单机可跑数千个；
- 提供 REST API 管理 VM 生命周期；
- **快照/恢复（snapshot/restore）**：把运行中的 VM 内存+设备状态落盘，恢复只需毫秒级——这是 Agent 沙箱"秒开一个带完整环境的沙箱"的关键技术；
- 配套 **jailer**：用 chroot + cgroups + seccomp + namespaces 把 Firecracker 进程本身再关一层。

最小启动流程（Linux + KVM）：

```bash
# 1. 准备 kernel(vmlinux) 与 rootfs(ext4)
# 2. 起 VMM 并配置
firecracker --api-sock /tmp/fc.sock &
curl --unix-socket /tmp/fc.sock -X PUT http://localhost/boot-source \
  -d '{"kernel_image_path":"vmlinux","boot_args":"console=ttyS0 reboot=k panic=1 pci=off"}'
curl --unix-socket /tmp/fc.sock -X PUT http://localhost/drives/rootfs \
  -d '{"drive_id":"rootfs","path_on_host":"rootfs.ext4","is_root_device":true,"is_read_only":false}'
curl --unix-socket /tmp/fc.sock -X PUT http://localhost/machine-config \
  -d '{"vcpu_count":2,"mem_size_mib":512}'
# 3. 启动
curl --unix-socket /tmp/fc.sock -X PUT http://localhost/actions \
  -d '{"action_type":"InstanceStart"}'
```

### 2.2 Cloud Hypervisor（Intel 发起，Rust）

与 Firecracker 类似的现代 VMM，设备模型稍丰富（支持 PCI 热插拔、VFIO 设备直通），适合需要 GPU/设备直通的场景。Kata 的默认 VMM 之一。

### 2.3 Kata Containers —— "VM 隔离 + 容器体验"

- 每个 Pod/容器跑在独立轻量 VM 里，VM 内是**真 Linux 内核**（兼容性 100%）；
- 对外仍是 OCI/CRI 接口：`docker run --runtime=kata` 或 K8s RuntimeClass；
- 代价：每 Pod 一个 VM 的内存底噪与启动时间（数百 ms–秒级）；
- 与 gVisor 的取舍见第 04 章第 5 节：**要完整兼容选 Kata，要高密度选 gVisor**。

## 3. 完整 VM：QEMU/KVM

- 设备模型最全，什么 OS 都能跑（Windows、老 Linux、BSD）；
- 启动秒级、内存底噪大，但支持 GPU 直通、嵌套虚拟化、完整快照；
- Agent 场景用法：**一次性 VM**——每个会话/任务起一台干净 VM，用完销毁（GitHub Actions 公共 runner 模式）；
- 云上等价物：每次任务起一台一次性 EC2/GCE 实例，用 cloud-init 注入环境。隔离最强、成本最高、冷启动最慢。

## 4. macOS 上的虚拟化（教学项目在 Mac 上怎么做）

Apple Silicon Mac 没有 KVM，对应物是 **Virtualization.framework**（macOS 11+）：

- 原生跑 Linux arm64 VM，性能接近原生（同一 CPU 架构，硬件虚拟化）；
- 上层工具：
  - **Lima**：`limactl start` 一条命令起 Linux VM，自动文件共享/端口转发，containerd 集成；
  - **UTM**：GUI 版 QEMU/Virtualization.framework；
  - **Colima / Docker Desktop**：Mac 上的 Docker 本来就跑在 Linux VM 里——所以"Mac 上的 Docker"天然多了一层 VM 边界（但文件共享目录仍是打通的，别被误导）；
  - **VZ + Rosetta**：可在 Linux VM 内跑 x86_64 二进制。
- 注意：Firecracker 需要 KVM，**不能直接在 macOS 上跑**；Mac 上实验 microVM 需先起一个支持嵌套虚拟化的 Linux VM（云上裸金属或支持 nested virt 的实例），或改用 Lima/Cloud Hypervisor 路线。

## 5. Agent 沙箱为什么偏爱 Firecracker + 快照

Agent 沙箱的理想形态：**每个会话一个强隔离环境，但要像函数调用一样快开**。

```
预热：基础镜像 VM 启动 → 装好工具链 → 在"就绪点"打快照
请求到达：从快照恢复（毫秒级）→ 注入工作区/任务 → 执行 → 销毁或再快照
```

- **E2B**：开源 Agent 沙箱云，核心就是 Firecracker microVM + 快照，SDK 一行 `Sandbox.create()`；
- **Fly.io Machines**：Firecracker VM 按需启停，API 驱动；
- **Modal**：gVisor 路线 + 自研镜像/快照调度，同样追求冷启动速度；
- **AWS Lambda**：SnapStart（Java）等也是快照思路的变体。

工程要点：

1. **快照含内存 = 含秘密**：快照文件要按敏感数据管理；恢复出的多个 VM 若共享同一快照，注意熵/随机数重复问题；
2. **网络编排**：每 VM 一个 tap 设备 + 独立 netns，出口经代理/防火墙做白名单；
3. **文件注入**：virtio-fs / vsock / 挂载专用数据盘，避免把宿主目录直接共享；
4. **生命周期**：超时强杀、磁盘配额、快照清理，防资源泄漏。

## 6. 各方案定位总结

| 方案 | 隔离 | 启动 | 兼容 | 典型 Agent 用法 |
|------|------|------|------|----------------|
| QEMU/KVM 完整 VM | 最强 | 秒级 | 完整 | 一次性任务 VM |
| Firecracker | 最强档 | ~125ms（快照更快） | 完整 | 多租户沙箱云（E2B/Lambda） |
| Cloud Hypervisor | 最强档 | ~百 ms | 完整 | 需要设备直通的沙箱 |
| Kata | 最强档 | 数百 ms–秒 | 完整 | K8s 里按 Pod 强隔离 |
| macOS Virtualization.framework | 强 | 秒级 | 完整（Linux arm64） | Mac 本地开发/教学 |
