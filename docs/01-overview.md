# 01 总览：Agent 为什么需要沙箱

## 1. 问题背景

AI Agent（尤其是 Coding Agent、数据分析 Agent、通用工具调用 Agent）的核心工作模式是：

```
用户意图 ──► LLM 生成 ──► 代码 / Shell 命令 / 工具调用 ──► 在真实环境执行 ──► 结果反馈给 LLM
```

关键事实：**LLM 生成的代码本质上是不可信输入**。它可能：

1. **无意破坏**：模型幻觉导致 `rm -rf` 错目录、死循环吃满 CPU、写坏配置文件；
2. **被提示注入（Prompt Injection）操纵**：Agent 读取的网页、README、依赖包、issue 内容中藏有恶意指令，诱导 Agent 执行攻击者想要的操作；
3. **主动或被诱导地作恶**：读取 `~/.ssh`、`~/.aws`、环境变量中的密钥并外传；安装后门；横向探测内网。

传统软件的安全边界是"程序员写的代码经过 review"，而 Agent 场景下**代码是运行时动态生成、无人 review 的**。因此必须把"执行环境"本身变成安全边界——这就是沙箱。

## 2. 威胁模型（Threat Model）

设计沙箱前先回答三个问题：

### 2.1 防谁？

| 威胁等级 | 描述 | 典型场景 |
|---------|------|---------|
| T1 防误操作 | 代码无恶意，但可能写错、删错、跑飞 | 本地 Coding Agent 日常使用 |
| T2 防不可信代码 | 代码可能恶意，但不假设它掌握 0day | 执行用户上传代码、跑第三方仓库的脚本 |
| T3 防定向攻击 | 攻击者知道你的沙箱方案，会尝试逃逸 | 多租户代码执行平台、公网 Agent 服务 |

### 2.2 保护什么？

- **文件系统**：工作区之外的文件不可读/不可写（尤其是密钥、浏览器数据、其他项目）；
- **网络**：不能任意外联（数据外传）、不能访问内网/云元数据服务（`169.254.169.254`）；
- **进程与内核**：不能 kill 宿主进程、不能 ptrace 别的进程、不能利用内核漏洞提权；
- **资源**：CPU/内存/磁盘/进程数有上限，不能 DoS 宿主机；
- **凭据**：宿主的环境变量、SSH agent、Docker socket 等不能透传进沙箱。

### 2.3 接受什么代价？

隔离强度不是免费的，代价体现在：

- **启动延迟**：进程级 ~毫秒，容器 ~百毫秒，microVM ~125ms–1s，完整 VM ~秒级；
- **资源开销**：每个 VM 要独立内核和内存底噪；gVisor 有 syscall 拦截开销；
- **兼容性**：越强的隔离越可能破坏程序假设（如 gVisor 未实现某些 syscall，容器里看不到真实 `/proc`）；
- **运维复杂度**：VM 需要镜像管理、网络编排、快照生命周期管理。

**没有"最好的沙箱"，只有匹配威胁模型的沙箱。** 本地个人助手用 T1 级软沙箱就够了；公网多租户代码执行服务必须按 T3 设计。

## 3. 隔离技术光谱

按隔离边界从弱到强排列：

```
┌────────────────────────────────────────────────────────────────────┐
│ 层级 0：进程内限制                                                  │
│   rlimit / ulimit、chroot、降权用户                                 │
│   边界：几乎没有。chroot 可被逃逸，只能防误操作                      │
├────────────────────────────────────────────────────────────────────┤
│ 层级 1：OS 软沙箱（第 02 章）                                       │
│   macOS Seatbelt(sandbox-exec)、Linux seccomp+namespaces+Landlock、 │
│   bubblewrap                                                       │
│   边界：同一内核，靠内核强制的访问规则过滤文件/网络/syscall           │
│   内核漏洞 = 逃逸                                                  │
├────────────────────────────────────────────────────────────────────┤
│ 层级 2：容器（第 03 章）                                            │
│   Docker / Podman / containerd                                     │
│   边界：本质上还是层级 1 的原语组合 + 镜像化的文件系统                │
│   "容器不是安全边界"——共享内核，攻击面大                            │
├────────────────────────────────────────────────────────────────────┤
│ 层级 3：用户态内核（第 04 章）                                      │
│   gVisor                                                           │
│   边界：Guest syscall 由用户态的 Sentry 重新实现，不直接打到宿主内核  │
│   宿主内核攻击面从 ~300+ syscall 缩到 ~几十个                       │
├────────────────────────────────────────────────────────────────────┤
│ 层级 4：虚拟机 / MicroVM（第 05 章）                                │
│   Firecracker、Cloud Hypervisor、Kata、QEMU/KVM                    │
│   边界：硬件虚拟化（VT-x/AMD-V + EPT），独立 Guest 内核              │
│   逃逸需要 VMM/hypervisor 漏洞，攻击面最小                          │
├────────────────────────────────────────────────────────────────────┤
│ 层级 5：物理隔离                                                    │
│   独立机器 / 一次性云实例                                           │
│   边界：硬件。成本最高，用于极端场景                                 │
└────────────────────────────────────────────────────────────────────┘
```

另有一个特殊分支：**语言级隔离**（V8 Isolate、WASM runtime）。Cloudflare Workers、Deno Deploy 用 V8 隔离跑不可信 JS，WASM 沙箱（wasmtime + WASI）跑不可信计算。它们启动极快（微秒–毫秒级），但只能跑特定语言/编译目标，不适合"任意 shell + 任意程序"的 Agent 场景，本系列不展开。

## 4. 各层速览对比

| 维度 | OS 软沙箱 | Docker | gVisor | MicroVM (Firecracker) | 完整 VM (QEMU/KVM) |
|------|----------|--------|--------|----------------------|-------------------|
| 内核共享 | 是 | 是 | 否（用户态重实现） | 否 | 否 |
| 启动时间 | ~ms | ~100ms–1s | ~150ms–1s | ~125ms 起 | 秒级 |
| 内存底噪 | 几乎为 0 | 几 MB | 十几 MB 起 | ~5MB VMM + Guest | 数百 MB 起 |
| syscall 兼容性 | 完整 | 完整 | 部分（~70–80% 常用） | 完整 | 完整 |
| I/O 性能 | 原生 | 原生 | 有开销（尤其文件/网络） | 接近原生（virtio） | 接近原生 |
| 逃逸难度 | 内核漏洞即可 | 内核漏洞即可 | 需攻破 Sentry + 宿主 | 需 VMM/hypervisor 漏洞 | 需 hypervisor 漏洞 |
| 典型用户 | Claude Code、Codex CLI 本地模式 | CI、开发环境 | GKE Sandbox、Modal | AWS Lambda、E2B、Fly.io | 传统云主机 |

## 5. 真实产品怎么选的

- **Claude Code / OpenAI Codex CLI（本地模式）**：macOS 用 Seatbelt（`sandbox-exec`），Linux 用 bubblewrap + Landlock + seccomp。理由：本地开发要毫秒级启动、完整 syscall 兼容、零额外内存，威胁模型是 T1–T2。
- **E2B**：Firecracker microVM，每个 Agent 会话一个 VM，配合快照实现快速冷启动。理由：公网多租户，T3。
- **Modal**：gVisor + 自研调度，容器体验 + 强于普通容器的隔离。
- **AWS Lambda / Fargate**：Firecracker。multi-tenant 函数计算的标杆答案。
- **GitHub Actions（公共 runner）**：一次性完整 VM，用完即毁。

可以看到一个规律：**本地单用户 → 软沙箱；云端多租户 → gVisor 或 microVM；极端不可信 → 一次性 VM**。

## 6. 沙箱不是银弹

即使有完美沙箱，仍有这些问题沙箱管不了：

1. **沙箱内的数据本身可能敏感**：Agent 在工作区里能读到的代码/数据，被注入后照样可以从允许的网络出口外传 → 需要网络出口白名单 + 审计（第 06 章）；
2. **权限授予（human-in-the-loop）**：沙箱外的操作（git push、发消息、花钱）需要审批机制，而不是靠沙箱；
3. **供应链**：沙箱里 `pip install` 的恶意包在沙箱内依然能作恶，沙箱只是把爆炸半径限制住；
4. **社会工程**：Agent 被诱导"请求用户批准"危险操作，防线在审批 UI 与策略。

正确的思路是**纵深防御**：沙箱（限制爆炸半径）+ 策略（限制能做什么）+ 审批（人在关键路径）+ 审计（事后可追溯）。
